# 设计取舍

## 场景与职责

客服问题处理的难点是完整处理多个诉求、补齐核验字段、获得政策依据，并在失败时留下可继续处理的上下文。General 负责接待和澄清，Technical 整理排障建议，Billing 核验账单字段，Escalation 整理人工交接。

多角色并不天然优于单 Agent，只在跨领域诉求出现时协作，避免为简单问答增加开销。升级节点当前不创建真实工单。

## 意图与 RAG

意图识别输出路由信号，RAG 补充回答证据。意图向量分支与知识库向量模型用途不同，切换前者不会改变后者。切片、召回、去重、排序属于检索链路，三路意图融合不是三路召回。

## 重试与幂等

用户请求带 client_request_id。会话锁避免同会话并发写入交错，Redis 事务保存消息与响应回执。已完成请求可读取原回执；进程在模型返回后、事务提交前崩溃时，重试仍可能再次消耗模型调用，不能保证外部模型恰好调用一次。

## 工具边界

调用经过白名单、参数校验、超时、缓存与熔断。外部 MCP 工具还受角色范围限制。缓存和角色隔离不能代替业务系统授权，当前账单计算与字段检查未查询真实支付系统。

## 验证证据

单元测试验证确定性行为，业务回放验证实际 HTTP 请求的结构、路由与工具选择，Judge 辅助检查对话质量。应分别报告三者的证据。演示集没有代表性保证，p95 也只有在相同模型、样本量与部署条件下才可比较。

## 本次改造范围

统一应用命名，新增订阅分诊 Skill，围绕 SaaS 客服问题重写展示说明，新增业务场景、虚构知识样例、HTTP 回放器与回执一致性检查。基础代码与这些改造分开提交，便于核对新增内容。新增 CI 配置用于 push/PR 测试；本地通过不等于远端 CI 已执行。
